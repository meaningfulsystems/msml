# Meaningful Systems Modeling Language (MSML) Requirements

## 1. Overview

MSML is a systems modeling language designed to be generated by AI and rendered by a Python tool. Design priorities, in order:

1. **AI-generatable** — the primary authors are LLMs; the format must be unambiguous, strictly typed, and free of syntax footguns
2. **One diagram per file** — each `.msml` file defines exactly one diagram; no multi-diagram container format in v1.0
3. **Visually prescriptive** — colors, sizes, and positions of every element are explicitly encoded; there is no automatic layout engine in v1.0
4. **Semantically rich** — supports all nine SysML 1.x diagram types with a SysML-standard diagram frame
5. **Python-native** — a Python library reads, validates, and renders `.msml` files to PNG

---

## 2. File Format

### 2.1 Extension and Encoding

- File extension: `.msml`
- Serialization format: **JSON** (parsed with Python's stdlib `json` module)
- Encoding: UTF-8
- **Exactly one diagram per file** — a file with multiple top-level `diagram` keys is a parse error

JSON is chosen over YAML because `.msml` files are generated by LLMs, not hand-authored. JSON has no implicit type coercion, no indentation sensitivity, no tab/space ambiguity, no multi-document syntax, and no special-case scalar parsing (the YAML "Norway problem" and boolean synonyms do not apply). Python's stdlib `json` parser is also significantly faster and requires no third-party dependency.

### 2.2 Top-Level Structure

```json
{
  "msml_version": "1.0",
  "diagram": {
    "type": "<DiagramType>",
    "id": "<string>",
    "name": "<string>",
    "context": "<string>",
    "description": "<string>",
    "frame": {
      "visible": true,
      "style": "<style>"
    },
    "canvas": {
      "width": "<int>",
      "height": "<int>",
      "background_color": "<color>",
      "grid": {
        "enabled": "<bool>",
        "size": "<int>",
        "snap": "<bool>"
      }
    },
    "elements": [],
    "relationships": [],
    "metadata": {
      "author": "<string>",
      "created": "<ISO 8601 date>",
      "modified": "<ISO 8601 date>",
      "tags": []
    }
  }
}
```

### 2.3 Diagram Frame

Every MSML diagram renders a SysML-standard diagram frame surrounding the canvas. The frame consists of:

1. **Outer rectangle** — a border drawn around the full canvas area
2. **Name tab** — a notched rectangle inset into the top-left corner of the frame containing the diagram header label

The header label follows the SysML convention:

```
<diagram_kind_abbreviation> [<context>] <diagram_name>
```

For example: `bdd [Vehicle] Vehicle Subsystems`

Standard abbreviations:

| Diagram Type | Abbreviation |
|---|---|
| Block Definition Diagram | `bdd` |
| Internal Block Diagram | `ibd` |
| Activity Diagram | `act` |
| Sequence Diagram | `sd` |
| State Machine Diagram | `stm` |
| Use Case Diagram | `uc` |
| Requirements Diagram | `req` |
| Parametric Diagram | `par` |
| Package Diagram | `pkg` |

The `context` field on the diagram is optional. When present it appears in square brackets in the tab. When absent the brackets are omitted.

The name tab notch is a fixed-width 45° chamfer on the bottom-right corner of the tab rectangle. Tab height and width are computed from the font metrics of the header label plus configurable padding.

Frame schema:

```json
{
  "frame": {
    "visible": true,
    "style": {
      "border_color": "#333333",
      "border_width": 1.5,
      "border_style": "solid",
      "fill_color": "#FFFFFF",
      "tab": {
        "fill_color": "#FFFFFF",
        "border_color": "#333333",
        "padding_x": 8,
        "padding_y": 4,
        "font": {
          "family": "Arial",
          "size": 11,
          "bold": false,
          "italic": false,
          "color": "#000000"
        }
      }
    }
  }
}
```

Element coordinates (`layout.x`, `layout.y`) are relative to the top-left corner of the **canvas interior** (inside the frame border). The renderer is responsible for offsetting element positions by the frame border width and tab height when compositing the final image.

### 2.4 Color Specification

Colors are specified as hex strings only — this keeps AI generation unambiguous:

- `"#RRGGBB"` — opaque color
- `"#RRGGBBAA"` — color with alpha channel

Named CSS colors and RGBA objects are not supported. The validator rejects any color value that does not match the hex pattern.

### 2.5 Position and Size

**All elements must carry explicit layout information in v1.0.** The parser raises `MSMLValidationError` if any element is missing its `layout` block or any of `x`, `y`, `width`, or `height`. There is no auto-layout fallback.

```json
{
  "layout": {
    "x": 0.0,
    "y": 0.0,
    "width": 200.0,
    "height": 100.0,
    "z_index": 0,
    "rotation": 0.0
  }
}
```

`x` and `y` are required. `z_index` (default `0`) and `rotation` (default `0.0`, degrees clockwise) are optional.

Relationship `waypoints` are required when a relationship exists; an empty array `[]` is permitted and renders a straight line from source to target center.

### 2.6 Connection Point Convention

When multiple relationships attach to the same side of an element, connection points are numbered **1 through 10** progressing **clockwise** around the element boundary. This ensures consistent, non-overlapping attachment positions.

**Clockwise direction by side:**

| Side   | Clockwise start | Clockwise end  | Axis that varies |
|--------|----------------|----------------|-----------------|
| Top    | Top-left       | Top-right      | x increases     |
| Right  | Top-right      | Bottom-right   | y increases     |
| Bottom | Bottom-right   | Bottom-left    | x decreases     |
| Left   | Bottom-left    | Top-left       | y decreases     |

**Formula** — for an element at `(x, y)` with `width` w and `height` h, connection point at position p (1–10):

| Side   | x coordinate              | y coordinate              |
|--------|--------------------------|--------------------------|
| Top    | `x + p * (w / 10)`       | `y`                      |
| Right  | `x + w`                  | `y + p * (h / 10)`       |
| Bottom | `x + w − p * (w / 10)`   | `y + h`                  |
| Left   | `x`                      | `y + h − p * (h / 10)`   |

**Example** — Idle block at `(310, 65)` with `w=260, h=60`:

| Side + position | Formula result | Meaning |
|----------------|----------------|---------|
| Top p=5 | x=440, y=65 | center top |
| Bottom p=5 | x=440, y=125 | center bottom |
| Bottom p=8 | x=362, y=125 | left-of-center bottom |
| Right p=3 | x=570, y=83 | upper-right |
| Right p=7 | x=570, y=107 | lower-right |
| Left p=5 | x=310, y=95 | center left |

This convention applies to the **first and last waypoint** of each relationship — those points should land exactly on an element edge following this formula. Intermediate waypoints are free-form routing bends. Up to 10 simultaneous connections per side are supported (one per position slot).

### 2.7 Diagram Type Naming

The `type` field in `diagram` always uses the **canonical long name**. The frame header abbreviation is derived by the renderer — authors never write it.

| Canonical `type` value | Frame abbreviation | File naming convention |
|---|---|---|
| `bdd` | `bdd` | `*-bdd.msml` |
| `ibd` | `ibd` | `*-ibd.msml` |
| `activity` | `act` | `*-act.msml` |
| `sequence` | `sd` | `*-seq.msml` |
| `state_machine` | `stm` | `*-stm.msml` |
| `use_case` | `uc` | `*-uc.msml` |
| `requirement` | `req` | `*-req.msml` |
| `parametric` | `par` | `*-par.msml` |
| `package` | `pkg` | `*-pkg.msml` |

`bdd` and `ibd` are their own canonical names (SysML-standard abbreviations that serve as both type and frame label).

### 2.8 Cross-Diagram References: `model_ref` and `type_ref`

Every element may carry two optional cross-reference fields.

**`model_ref`** — a stable logical identifier independent of file or diagram, in dot-notation:
```json
{ "model_ref": "Toaster.HeatingElement" }
```
Used by tooling and validators to link elements across diagrams. Not resolved by the v1.0 parser; treated as opaque metadata. Lint mode warns if the value is not valid dot-notation.

**`type_ref`** — identifies the classifier (block, interface, etc.) that types this element. In v1.0 it is a plain string naming the classifier. In v1.1 it will support file-relative resolution (`"toaster-bdd.msml#block-element"`):
```json
{ "type_ref": "HeatingElement" }
```
Strict mode validates that if `type_ref` matches an element `id` within the same file, the referenced element is a valid classifier type (e.g., `block`, `interface_block`).

### 2.9 Visual Style

Every element may carry a `style` block:

```json
{
  "style": {
    "fill_color": "#DDEEFF",
    "border_color": "#336699",
    "border_width": 2.0,
    "border_style": "solid",
    "opacity": 1.0,
    "corner_radius": 0.0,
    "shadow": {
      "enabled": false,
      "color": "#00000044",
      "offset_x": 2.0,
      "offset_y": 2.0,
      "blur": 4.0
    },
    "font": {
      "family": "Arial",
      "size": 12.0,
      "color": "#000000",
      "bold": false,
      "italic": false,
      "underline": false
    }
  }
}
```

`border_style` must be one of: `"solid"`, `"dashed"`, `"dotted"`, `"none"`.

## 3. Diagram Types

MSML supports all nine SysML 1.x diagram types. Each diagram type is identified by the `type` field.

### 3.1 Block Definition Diagram (`bdd`)

Models the hierarchical structure and properties of system blocks.

**Element types:**
- `block` — system component with properties and operations
- `value_type` — typed value (quantity, unit)
- `interface_block` — port interface definition
- `actor` — external actor
- `constraint_block` — parametric constraint block
- `comment` — annotation

**Relationship types:**
- `association`
- `composition`
- `aggregation`
- `generalization`
- `dependency`
- `realization`

**Block element schema:**
```json
{
  "type": "block",
  "id": "<string>",
  "name": "<string>",
  "stereotype": "<string>",
  "is_abstract": false,
  "compartments": {
    "properties": [
      {"name": "<string>", "type": "<string>", "multiplicity": "1", "default_value": null}
    ],
    "operations": [
      {
        "name": "<string>",
        "parameters": [
          {"name": "<string>", "type": "<string>", "direction": "in"}
        ],
        "return_type": "<string>"
      }
    ],
    "constraints": [
      {"name": "<string>", "expression": "<string>"}
    ],
    "ports": [
      {
        "id": "<string>",
        "name": "<string>",
        "direction": "provided",
        "type": "<string>",
        "layout": {"side": "left", "offset": 0.0}
      }
    ]
  },
  "layout": {"x": 0.0, "y": 0.0, "width": 200.0, "height": 120.0},
  "style": {}
}
```

`direction` on ports: `"provided"` | `"required"`. `direction` on operation parameters: `"in"` | `"out"` | `"inout"` | `"return"`.

### 3.2 Internal Block Diagram (`ibd`)

Models the internal structure and port connections of a block.

**Element types:**
- `part` — part property instance
- `port` — interaction point (full, proxy, or flow)
- `connector` — connection between ports
- `reference` — reference property

**IBD-specific port schema:**
```json
{
  "type": "port",
  "id": "<string>",
  "name": "<string>",
  "owner_ref": "<id_ref>",
  "port_type": "full",
  "direction": "in",
  "interface_block": "<id_ref>",
  "flow_specification": "<id_ref>",
  "layout": {"x": 0.0, "y": 0.0, "width": 12.0, "height": 12.0, "side": "left", "offset": 0.0},
  "style": {}
}
```

`owner_ref` — required in `strict` mode; identifies the `part` element that owns this port. The renderer uses explicit coordinates; `owner_ref` is used by the validator to confirm the port lies on or adjacent to its owner's boundary.

`port_type`: `"full"` | `"proxy"` | `"flow"`. `direction`: `"in"` | `"out"` | `"inout"`.

### 3.3 Activity Diagram (`activity`)

Models sequential and concurrent behaviors.

**Element types:**
- `initial_node`
- `activity_final_node`
- `flow_final_node`
- `action` — executable action with optional input/output pins
- `decision_node`
- `merge_node`
- `fork_node`
- `join_node`
- `object_node` — data store or buffer
- `send_signal_action`
- `accept_event_action`
- `call_behavior_action`
- `partition` — swim lane

**Relationship types:**
- `control_flow`
- `object_flow`

**Action schema:**
```json
{
  "type": "action",
  "id": "<string>",
  "name": "<string>",
  "kind": "opaque",
  "pins": {
    "input": [{"id": "<string>", "name": "<string>", "type": "<string>"}],
    "output": [{"id": "<string>", "name": "<string>", "type": "<string>"}]
  },
  "partition_ref": "<id_ref>",
  "layout": {"x": 0.0, "y": 0.0, "width": 160.0, "height": 60.0},
  "style": {}
}
```

`kind`: `"opaque"` | `"call_behavior"` | `"call_operation"` | `"send_signal"` | `"accept_event"`.

### 3.4 Sequence Diagram (`sequence`)

Models time-ordered message exchanges between lifelines.

**Element types:**
- `lifeline`
- `execution_occurrence` — activation bar
- `combined_fragment` — alt, opt, loop, par, critical, break, neg, ref, consider, ignore, assert
- `interaction_operand`
- `destruction_occurrence`
- `gate`

**Relationship types:**
- `message` — synchronous, asynchronous, reply, create, destroy, found, lost

**Sequence-specific layout:**

Lifelines are positioned by `x` offset (column). Messages carry a `sequence_number` and `y` coordinate indicating vertical ordering.

```json
{
  "type": "lifeline",
  "id": "<string>",
  "name": "<string>",
  "represents": "<string>",
  "create_message": "<id_ref>",
  "layout": {"x": 0.0, "y": 0.0, "width": 120.0, "height": 400.0, "head_height": 40.0},
  "style": {}
}
```

```json
{
  "type": "message",
  "id": "<string>",
  "name": "<string>",
  "source_lifeline": "<id_ref>",
  "target_lifeline": "<id_ref>",
  "message_sort": "synch_call",
  "sequence_number": "1",
  "arguments": [],
  "layout": {"y": 100.0},
  "style": {
    "line_color": "#333333",
    "line_width": 1.5,
    "line_style": "solid",
    "source_arrowhead": "none",
    "target_arrowhead": "filled"
  }
}
```

`message_sort`: `"synch_call"` | `"asynch_call"` | `"asynch_signal"` | `"reply"` | `"create"` | `"destroy"` | `"found"` | `"lost"`. Messages use a simplified `layout` with only `y` (vertical position on canvas); `x` is derived from the source and target lifeline positions.

### 3.5 State Machine Diagram (`state_machine`)

Models reactive behavior through states and transitions.

**Element types:**
- `initial_pseudostate`
- `final_state`
- `state` — simple, composite, or orthogonal
- `choice_pseudostate`
- `junction_pseudostate`
- `shallow_history_pseudostate`
- `deep_history_pseudostate`
- `entry_point`
- `exit_point`
- `terminate_pseudostate`

**Relationship types:**
- `transition`

**State schema:**
```json
{
  "type": "state",
  "id": "<string>",
  "name": "<string>",
  "kind": "simple",
  "entry": "<string>",
  "do": "<string>",
  "exit": "<string>",
  "regions": [
    {"id": "<string>", "name": "<string>", "elements": ["<id_ref>"]}
  ],
  "layout": {"x": 0.0, "y": 0.0, "width": 160.0, "height": 80.0},
  "style": {}
}
```

```json
{
  "type": "transition",
  "id": "<string>",
  "source": "<id_ref>",
  "target": "<id_ref>",
  "trigger": "<string>",
  "guard": "<string>",
  "effect": "<string>",
  "waypoints": [{"x": 0.0, "y": 0.0}],
  "style": {
    "line_color": "#333333",
    "line_width": 1.5,
    "line_style": "solid",
    "source_arrowhead": "none",
    "target_arrowhead": "open",
    "label_offset": {"x": 0.0, "y": 0.0}
  }
}
```

`kind`: `"simple"` | `"composite"` | `"orthogonal"`.

### 3.6 Use Case Diagram (`use_case`)

Models system functionality from the user perspective.

**Element types:**
- `actor`
- `use_case`
- `system_boundary`
- `subject`

**Relationship types:**
- `association`
- `include`
- `extend`
- `generalization`
- `dependency`

**Extension point schema (use_case element):**
```json
{
  "type": "use_case",
  "id": "<string>",
  "name": "<string>",
  "extension_points": [
    {"name": "<string>", "condition": "<string>"}
  ],
  "layout": {"x": 0.0, "y": 0.0, "width": 140.0, "height": 60.0},
  "style": {}
}
```

### 3.7 Requirements Diagram (`requirement`)

Captures textual requirements and their relationships.

**Element types:**
- `requirement`
- `test_case`
- `block` — satisfying or verifying element (cross-ref)
- `comment`

**Requirement schema:**
```json
{
  "type": "requirement",
  "id": "<string>",
  "name": "<string>",
  "req_id": "REQ-001",
  "text": "<string>",
  "kind": "functional",
  "priority": "high",
  "status": "proposed",
  "layout": {"x": 0.0, "y": 0.0, "width": 240.0, "height": 100.0},
  "style": {}
}
```

`kind`: `"functional"` | `"performance"` | `"interface"` | `"physical"` | `"design_constraint"` | `"extended"`. `priority`: `"high"` | `"medium"` | `"low"`. `status`: `"proposed"` | `"approved"` | `"deprecated"`.

**Relationship types:**
- `derive`
- `satisfy`
- `verify`
- `refine`
- `trace`
- `copy`
- `containment`

### 3.8 Parametric Diagram (`parametric`)

Models constraint networks for quantitative analysis.

**Element types:**
- `constraint_property` — instantiation of a constraint block
- `value_property` — bound parameter
- `binding_connector`

**Parametric schema:**
```json
{
  "type": "constraint_property",
  "id": "<string>",
  "name": "<string>",
  "constraint_block_ref": "<id_ref>",
  "parameters": [
    {"id": "<string>", "name": "<string>", "type": "<string>", "bound_to": "<id_ref>"}
  ],
  "layout": {"x": 0.0, "y": 0.0, "width": 180.0, "height": 80.0},
  "style": {}
}
```

### 3.9 Package Diagram (`package`)

Organizes model elements into namespaced packages.

**Element types:**
- `package`
- `model`
- `profile`
- `stereotype`
- `class`
- `element_import`
- `package_import`

**Relationship types:**
- `package_merge`
- `package_import`
- `element_import`
- `dependency`
- `profile_application`

## 4. Common Relationship Schema

All relationships share a base schema extended by diagram-specific fields:

```json
{
  "type": "<relationship_type>",
  "id": "<string>",
  "name": "<string>",
  "source": "<id_ref>",
  "target": "<id_ref>",
  "multiplicity_source": "<string>",
  "multiplicity_target": "<string>",
  "waypoints": [{"x": 0.0, "y": 0.0}],
  "label_position": {"x": 0.0, "y": 0.0},
  "style": {
    "line_color": "#333333",
    "line_width": 1.5,
    "line_style": "solid",
    "corner_radius": 10,
    "source_arrowhead": "none",
    "target_arrowhead": "open"
  }
}
```

`line_style`: `"solid"` | `"dashed"` | `"dotted"`. `source_arrowhead` / `target_arrowhead`: `"none"` | `"open"` | `"filled"` | `"diamond"` | `"open_diamond"` | `"composition"` | `"aggregation"`.

`corner_radius` (default `10`) — polyline bends are replaced with quadratic bezier arcs of this radius. Set to `0` to disable rounding. Rounded corners are the default for all relationship types.

## 5. Python Library Requirements

### 5.1 Core Modules

| Module | Responsibility |
|---|---|
| `msml.parser` | Load and validate `.msml` files (JSON → Python objects) |
| `msml.model` | Dataclass / Pydantic model hierarchy for all element types |
| `msml.validator` | Schema validation, referential integrity checks (schema / strict / lint modes) |
| `msml.renderer` | PNG rendering via Pillow (PIL) |
| `msml.serializer` | Python objects → JSON serialization |
| `msml.cli` | Command-line interface |

### 5.2 Parser Requirements

- Parse a `.msml` file into a `Diagram` model object using Python's stdlib `json` module (no third-party dependency)
- Raise `MSMLParseError` with file path and character offset on malformed JSON
- Raise `MSMLValidationError` with element ID and field name on schema violations
- No `include` or import directives — each file is self-contained; composition is done by the AI generator, not the parser

### 5.3 Model Requirements

- All diagram elements modeled as Python dataclasses or Pydantic v2 models
- Full type annotations on all fields
- `layout.x`, `layout.y`, `layout.width`, `layout.height` are required fields with no defaults — the model raises on construction if absent
- Default values only for optional visual fields (color defaults to diagram-type presets, `z_index` defaults to 0, `rotation` defaults to 0)
- `to_dict()` / `from_dict()` round-trip methods for every model

### 5.4 Validator Requirements

Validation runs in three modes, each a superset of the previous:

**`schema` mode (default)**
- Every `id` is unique within a diagram
- Every `<id_ref>` resolves to an existing element within the same file
- Every element has `layout.x`, `layout.y`, `layout.width`, and `layout.height` — missing any of these is a hard error
- Numeric ranges: `opacity` in `[0.0, 1.0]`, `z_index >= 0`, `border_width >= 0`
- All color values match `#RRGGBB` or `#RRGGBBAA` pattern
- `diagram.type` is one of the nine canonical values
- `message_sort` values are valid for the diagram type
- All relationship `type` values are valid for the diagram type

**`strict` mode (`--strict`)**
- Everything in `schema` mode, plus:
- Unknown fields in any element or relationship are errors
- `owner_ref` is required on all `port` elements in IBD diagrams
- `type_ref` must resolve to an existing element `id` within the same file when present
- Sequence diagram: message lifeline IDs (`source_lifeline`, `target_lifeline`) must reference `lifeline` elements
- Sequence diagram: message `layout.y` values must be monotonically increasing
- All `source_arrowhead` and `target_arrowhead` values are from the allowed enum (no `arrowhead` shorthand)

**`lint` mode (`--lint`)**
- Everything in `strict` mode, plus warnings (do not block rendering):
- Font size below 9pt on any element
- Canvas utilization below 40% (content bounding box vs canvas area)
- Relationship endpoint (first or last waypoint) not within 5px of any element boundary
- Any BDD `block` element not referenced by at least one IBD `part.type_ref` in the same file
- Any `requirement` element with no incoming `satisfy`, `verify`, or `derive` relationship
- `model_ref` present but malformed (not `Namespace.Path` dot-notation)
- Estimated label text width exceeds element width (overflow warning)

### 5.5 Renderer Requirements

- Output format is PNG (RGBA) via Pillow; no SVG output in v1.0
- DPI is configurable (default 96); canvas pixel dimensions in the file map 1:1 to output pixels at 96 DPI
- The renderer draws the diagram frame and name tab before drawing any canvas elements
- Element coordinates are offset by frame border width and tab height when compositing
- Renderer must honor all `layout` and `style` fields exactly — no adjustment or normalization of author-specified positions
- Text wrapping within element bounds
- Arrowhead and line-end rendering per relationship style

### 5.6 Serializer Requirements

- Round-trip fidelity: `parse(serialize(diagram)) == diagram`
- Output JSON preserves logical grouping (elements before relationships)
- Optional `--compact` mode omits fields equal to their defaults
- IDs are stable across serialize/parse cycles

### 5.7 CLI Requirements

```
msml render <file.msml> [--output <path>] [--dpi <int>]
msml validate <file.msml> [--strict] [--lint]
msml convert <file.msml> --to <format>   # future: PlantUML, SysML XMI
msml new <diagram_type> [--name <name>]  # scaffold a new blank diagram
msml info <file.msml>                    # print diagram type, element count, dimensions
```

Output of `msml render` is always PNG. If `--output` is omitted the PNG is written alongside the `.msml` file with the same base name.

## 7. Extensibility

### 7.1 Custom Stereotypes

Users may define custom stereotypes with associated default styles in a separate profile file (also JSON, `.msml-profile` extension):

```json
{
  "profile": {
    "name": "MyProfile",
    "stereotypes": [
      {
        "name": "sensor",
        "extends": "block",
        "icon": "./icons/sensor.png",
        "style": {
          "fill_color": "#E8F5E9",
          "border_color": "#2E7D32"
        }
      }
    ]
  }
}
```

### 7.2 Custom Element Types

Third-party libraries may register new element types via Python entry points:

```
msml.elements = mypackage.elements:CustomElementRegistry
```

### 7.3 Diagram Templates

The `msml new` command generates a scaffold `.msml` file with placeholder elements at explicit default positions. All generated files are valid v1.0 files — no position fields are omitted.

---

## 8. Constraints and Limitations (v1.0)

- **One diagram per `.msml` file** — multi-diagram model files are a v2 concern
- **All element positions are required** — `layout.x`, `layout.y`, `layout.width`, `layout.height` must be present on every element; missing values are parse errors
- **Output is PNG only** — SVG and other export formats are v2
- No automatic layout engine — positions must be authored explicitly
- No built-in simulation or execution semantics
- No graphical editor — files are authored by hand or generated programmatically
- Cross-diagram references use file-relative paths and element IDs; no global namespace resolution in v1

## 10. Open Questions for Future Versions

- **Auto-layout (v2)**: Support optional layout algorithms (e.g., ELK, Graphviz) that compute positions when `layout` is omitted
- **SVG export (v2)**: Add SVG as an additional output format alongside PNG
- **XMI export**: SysML 2.0 uses a textual notation; should MSML support export to SysML 2.0 or XMI?
- **Multi-diagram models (v2)**: Allow a `.msml` file to define multiple diagrams sharing a common model namespace
- **Live rendering**: A watch mode (`msml watch`) that re-renders on file save, similar to PlantUML's preview server
- **Constraint evaluation**: Should parametric diagrams support symbolic math evaluation (e.g., via SymPy)?
